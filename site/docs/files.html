The folder is the API

Everything the MCP serves is a plain JSON file in the folder you picked, written by the phone, readable by anything. The MCP is a convenience on top. Here is the layout, an example file trimmed to its shape, and the rules.

Layout

Health Access/                            # the folder you picked, any name
  index.json                              # one row per workout, newest first; the app rewrites it after every export
  briefing.md                             # one page any AI can read
  workouts/
    2026-05-14_0712_PoolSwim_7A1C3E90.json   # <local date_time>_<Activity>_<first 8 of the HealthKit UUID>
    2026-05-12_0630_IndoorRow_3F8B2D41.json
  vitals/
    2026-05-14.json                       # one per day, rewritten when values change
  days/
    2026-05-14.json                       # one per day, every Health group (v0.4; vitals/ stays for one release)
  catalog.json                            # which Health types have data, and where each was exported (v0.4)
  profile.json                            # age, birth year, sex, blood type, move mode (v0.4)
  plans/
    2026-05-13T19:02:11Z-s12.json         # written by your AI (push_plan) or the CLI
    2026-05-13T19:02:11Z-s12.status.json  # written by the app: did it reach the Watch
  mcp/clients/
    <id>.json                             # presence file written by the MCP: client, machine, counts

Who writes what

PathWritten byRead by
workouts/*.jsonThe app, once per workout. Never overwritten by export. The MCP or CLI may update exactly two keys, effort and feel, through rate_workout.MCP, CLI, your AI, you
vitals/*.jsonThe app, today and yesterday on every run; 30-day backfill from Settings.MCP, CLI, your AI
days/*.json, catalog.json, profile.jsonThe app, from v0.4: every Health group per day, the list of types with data and where each was exported, the athlete's characteristics.MCP, CLI (healthaccess day, catalog, profile; doctor checks the coverage), your AI
index.jsonThe app, after every export and every rating. The MCP updates a row's effort after rate_workout, never adds rows.MCP (for listing), CLI
plans/<id>.jsonThe MCP (push_plan) or the CLI (healthaccess plan push). Your AI can also write it directly.The app
plans/<id>.status.jsonThe app, after "Put on Watch".MCP (get_plan_status, list_plans)
briefing.mdThe app, after every sync.Any AI, a coach, you
mcp/clients/<id>.jsonThe MCP, on start and after tool calls, at most once a minute: client name and version, machine name, call count, last tool name. Never arguments or results.The app, to show "Connected · Claude Code on Alex's MacBook Pro · last seen 2 min ago"

Nothing else writes. Nothing ever deletes: a duplicate workout (same start within 2 seconds, same source) stays on disk and is left out of index.json. All JSON is UTF-8 with sorted keys; all timestamps are ISO 8601 in UTC with a Z; the local time is in the file name and in metadata.HKTimeZone.

What the fields mean

activity
pool_swim, open_water_swim, indoor_row, run, walk, cycle, or other:<HealthKit raw type>.
zones
Not written any more. Zone seconds are computed by the MCP and the command line from hr_series, with the four upper bounds from zone_bounds in ~/.config/healthaccess/config.toml or, without them, an estimate from the age in profile.json (max heart rate 208 minus 0.7 times age; zones end at 72, 79, 86 and 92 percent of it). Every zone result says which it used (bounds_source). Files from before v0.4 may still carry app-computed zones; they are accepted.
steps
One per interval of a structured workout. key is Apple's block.rep.step, with 0.0.0 the warm-up and a trailing single step the cool-down. label is the step name from the plan your AI wrote; Apple drops step names on the way to HealthKit, so the app joins them back from the matching plan. A free workout has steps: [].
laps
One per pool length: stroke (freestyle, backstroke, breaststroke, butterfly, mixed, kickboard) and SWOLF.
hr_series
Heart rate about every 5 seconds, at least 4 seconds apart. The MCP leaves it out unless asked.
recovery_hr
Heart rate at the end, one minute and two minutes after. null right after a background export; filled in on the next run.
effort, feel
Your rating, 1 to 10, and a line of text. The rating comes from your Watch, which asks after a workout; Apple exports it and the file says effort_source: apple. The app never asks. rate_workout writes ai after you told the AI a number; files from older builds may say app. effort_estimated is Apple's own estimate and is never used as your effort.
plan_ref
The plan this session was started from, matched by the WorkoutKit id the app recorded, else by sport and scheduled time within two hours. null for a workout started on the Watch by hand.
metadata
Apple's raw workout metadata as strings. HKLapLength is where the pool length comes from.

Vitals, one file per day

{
  "schema": "healthaccess.vitals.v1",
  "date": "2026-05-14",
  "resting_hr": 54,
  "hrv_sdnn_ms": 58.3,
  "sleep_s": 26160,
  "body_mass_kg": 78.4,
  "steps": 9412,
  "vo2max": 44.1,
  "bp": null
}

Every field can be null; a day on which only steps were recorded gives a file full of nulls. Sleep is credited to the morning it ended and summed from the one source with the most sleep, so Watch and iPhone are not double-counted. HRV is the day's average; resting heart rate, weight, VO2max and blood pressure are the day's latest. A day with no values gets no file.

days/, one file per day with everything v0.4

From v0.4 the app writes days/<date>.json next to vitals/, with every Health group that has data that day: activity (the rings, steps, distances, energy, exercise and stand minutes, daylight), heart, respiratory, sleep (stages and sessions), body, blood, mobility, hearing, nutrition, mind, symptoms, cycle, medications, hygiene, uv, wheelchair. A group is present only when it has data; inside a present group, absent values are an explicit null. The example day, trimmed to three groups:

Two more files come with it. catalog.json lists every HealthKit type the app knows, with has_data, the sample count over 90 days, first and last date, and exported_in (workouts, days, ecg, profile or none), so healthaccess doctor can say "a type with data was exported nowhere" the day it happens. profile.json carries age and birth year (not the birthday), biological sex, blood type, wheelchair use, move mode and skin type. The full contract: docs/export-coverage.md.

Newest first, no series. The MCP lists from the index and opens a workout file only on demand. If the index lags behind the files, which happens, ids are also resolved by scanning workouts/.

Plans and their status

Your AI writes plans/<id>.json; the app answers with plans/<id>.status.json. The format, the rules and the "Put on Watch" flow have their own page. The status file for the plan behind the example swim, as the app wrote it after WorkoutKit scheduled the session for the next morning:

{
  "plan_id": "2026-05-13T19:02:11Z-s12",
  "state": "scheduled",
  "at": "2026-05-13T19:04:40Z",
  "method": "schedule",
  "workoutkit_id": "D4E7A2C1-6F3B-4E8A-9B5C-1A2F3E4D5C6B",
  "scheduled_for": "2026-05-14T05:00:00Z",
  "error": null
}

mcp/clients/<id>.json

The one file the MCP writes that is not a plan: a presence note, so the app can show that an AI is connected. Written on server start and after tool calls, at most once a minute, one file per machine and client, overwritten in place. It never contains tool arguments or results.

{
  "schema": "healthaccess.client.v1",
  "id": "9f3c1a7e5b2d4c80",
  "client": {
    "name": "Claude Code",
    "version": "2.1.0"
  },
  "machine": "Alex's MacBook Pro",
  "mcp_version": "0.2.0",
  "first_seen": "2026-05-09T17:20:41Z",
  "last_seen": "2026-05-14T06:11:02Z",
  "last_tool": "list_workouts",
  "calls": 123
}

The app shows "Connected · Claude Code on Alex's MacBook Pro · last seen 2 min ago" when any file in the folder is newer than 7 days, else "Not connected yet".

briefing.md

One page of Markdown the app rewrites after every sync, so an AI without the MCP (ChatGPT, a Claude Project, a local model, a human coach) still gets the picture. Sections, in this order: the title with the athlete's name and the time written; Last 4 weeks, one line per ISO week with sessions, distance, time and mean effort; Recent sessions, newest first, at most ten, one line each; Vitals, the latest resting heart rate, HRV, sleep and weight with their dates and the 21-day direction; Next session, the newest plan not yet on the Watch; Open, unrated sessions and plans waiting for a tap; Limits, the two fixed sentences about unlocking and pool length. No charts, no JSON, under 60 lines. An example: examples/briefing.md.

Files from before the rename

The project was called "Tide" until 2026-10-25. Files written before that carry "schema": "tide.workout.v1" (or tide.workout.v0, the first format), tide.vitals.v1, tide.index.v1, tide.plan.v1, and the key tide_version instead of healthaccess_version. Every reader accepts both for good; nothing is rewritten just to change a tag. The same goes for the environment variable TIDE_DIR and the resource URIs tide://index and tide://workout/<id>.

The complete contract, with every field and the deviations the app documents, is docs/schema.md in the repository.
